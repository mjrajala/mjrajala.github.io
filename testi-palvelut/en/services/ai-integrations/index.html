AI integrations: ERP, CRM and the rest of your systems.

AI only becomes useful once it can reach the data where the work actually lives: resource planning, customer relationship management, invoicing and the document store. We build the connection and define what it is allowed to read and what it is allowed to write.

What we do

  • The connection itself

    First we work out how the system can be reached and with which rights. This step decides whether the integration is days or weeks of work.

    • Interface survey: REST, SOAP, file transfer or a database view
    • Authentication with a service account, not a person’s credentials
    • Field mapping, mandatory fields and value lists
    • A test run on copied data before production

  • Read and write, decided separately

    A read-only integration carries less risk than a writing one, because it changes nothing. It is not risk-free: read access can expose more material than the task needs, so it gets scoped as carefully as a write.

    • Read access limited to the records and fields the task needs
    • Writes enabled by a separate decision, not in the same step
    • Writes limited to named fields and record types
    • Human approval before an irreversible entry
    • A log of which record changed, on what data and who approved it

  • When things break

    An integration will fail at some point, and what matters then is what was agreed to happen. That gets designed before go-live, not after.

    • Behaviour during an outage: queue, retry or a clean stop
    • Duplicate protection when the same message arrives twice
    • Exceptions routed to a person instead of being guessed
    • An alert when the connection fails or an entry is rejected

What an integration is and isn’t

An integration moves data. It does not fix data.

An integration brings a system’s data to where it is needed and writes the result back. If the source system holds incomplete customer records or two versions of the same product, the integration moves them exactly as they are. Cleaning up is separate work, and it is worth doing before an automation starts trusting the data.

We don’t sell ready-made connectors for particular products. Which system you connect to, and how deeply, becomes clear once the interface, the version and the access rights have been reviewed. In some systems the interface is open and documented, in some it has to be ordered from the vendor, and in some the only route is a file transfer. We tell you which case you are in before we estimate any effort.

What an integration does not do

  • It does not replace a missing interface. If the system won’t let data out, that is a conversation with the vendor.
  • It does not clean the source data. Wrong data moves across as wrong data until it is fixed at the source.
  • It does not move responsibility. An entry is in your books and on your responsibility even when an automation made it.

Examples of scopes worth starting from

  • A quote draft whose line items and prices come from resource planning, for a salesperson to check
  • A summary of a customer conversation written into the CRM once the salesperson has approved it
  • Purchase invoice lines matched against the order and the delivery, with exceptions listed for a person
  • Customer service asking for a stock balance or a delivery date in one question, without opening the system
  • Document metadata written into the system as soon as a file arrives

Decide before building

  1. Which system, which version, and whether an interface already exists.
  2. Who owns the service account and which rights it is given.
  3. Which data is read and which data is written back.
  4. Which entries need human approval, and who approves them.
